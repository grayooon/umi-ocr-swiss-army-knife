项目最低目标系统是 **Windows 7 x64**。按照作者的安排，Win7 由作者迁移到真实电脑测试，不进行模拟系统兼容性推断。

HyperLPR3 的 `__init__.py` 由作者确认原本存在，只是附件漏传；本次提供的入口用于补齐交付目录，未对漏传的原文件作内容审查。

## A. 作者沿用现有依赖迁移测试

1. 完全退出当前 Umi-OCR，包括托盘程序。复制整个已经可用的 Umi-OCR 作为备份。
2. 再复制一份作为“候选版测试目录”，保留其 `runtime`、三个插件的 `site-packages` 和模型。无需重新下载依赖。
3. 对每个插件，将旧的 `tools` 文件夹改名为 `tools.original-backup`，然后复制本候选版相应插件里的核心文件、完整 `tools` 和文档到该插件目录，覆盖同名核心文件。旧版根目录中不再使用的文件不会作为新入口；正式打包时应使用本候选版干净源码目录。
4. **这条路径不要运行 `01_setup_online.bat`、`install_deps.bat`、`03_setup_offline.bat`。** 它们会安装清单中的依赖，不能拿它们覆盖你可能已经验证兼容的依赖。
5. 可以先运行 `tools\04_export_environment.bat`，生成 `environment-report.json`。该脚本只读取文件版本与散列，报告留在本地，不自动上传。
6. 在 Win10 上逐个运行 `tools\02_self_check.bat`，再在 Umi 内完成下方用例。通过后，将整套候选版测试目录迁移到 Win7 实机，同样执行。
7. 如候选版失败而原版通过，用备份恢复。保留报错、环境报告和具体步骤，以定位是本次修订、依赖还是系统差异，不要混合替换多个来源不明的 DLL。

这条路径通过后，可以表述“这套现有依赖在这些实机上测试通过”，不能直接表述“任何人从互联网全新下载也已通过”。

## B. 全新下载部署测试

在另一份干净 Umi-OCR 中，从 GitHub 下载候选版源码，按 README 复制插件，运行 `01_setup_online.bat`。记录下载清单版本和自检结果，再完成下方用例。

目前 Win7 的依赖下载会在覆盖任何依赖前明确停止，原因是已知官方 ORT 导入了 `GetSystemTimePreciseAsFileTime`。该 API 的最低客户端为 Windows 8。[Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemtimepreciseasfiletime)

如果 A 路径 Win7 成功，后续应锁定那套可用文件：

1. 保留实际 `site-packages`、模型和三份环境报告。
2. 核实 Win7 兼容 ORT 是哪一版本/构建，原始下载链接、补丁与构建方式是什么；如果系统安装了兼容层，也要明确记录。
3. 检查整套依赖的许可证和重新分发条件，保留 `.dist-info` 中的 LICENSE/NOTICE 等文件。
4. 为可用 Win7 包建立单独的文件清单和 SHA-256，提供明确的 Win7 下载入口或缓存准备包，再补充安装器分支。
5. 在一台没有预先拷贝私人依赖的 Win7 电脑上，按公开 README 从零部署。通过后才完成“普通用户联网下载 → Win7 离线使用”的闭环。

不能只把 DLL 改名成旧版本，也不能简单降级 ORT 后手改模型 IR 数字。PP-OCRv6 模型与 ORT 的格式支持需要同时满足；旧 ORT 对较新 IR 的支持并不会因改文件名而增加。[ORT 模型兼容表](https://onnxruntime.ai/docs/reference/compatibility.html)

## D. 日志判读

- `[PASS]`：自检使用了真实图片、得到非空结果、三种输入一致；仍需人工核对文字。
- `[INCOMPLETE]`：缺图片或识别无文字，不能算完成验收。
- `[FAIL]`：记录完整报错与复现步骤。
- `Your argv: ...`：启动器日志会被通信层跳过，单独出现不构成错误。
- 环境报告只说明文件版本和内容指纹，不替代识别测试，也不证明文件无恶意。
